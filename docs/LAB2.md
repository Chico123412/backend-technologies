# Лабораторна №2 — Unit-тестування

Тестується існуючий каталог послуг автосервісу з першої лабораторної.
Основний клас бізнес-логіки — `CatalogService`. Його реалізація не змінюється.

## Запуск

```bash
./mvnw clean verify
```

Команда запускає лише модульні тести, створює HTML/XML/CSV звіти JaCoCo
і перевіряє покриття рядків: щонайменше 60% для всього написаного коду,
100% для `CatalogService`.
Із підрахунку виключена лише згенерована MapStruct реалізація `ServiceMapperImpl`.
Сутність, DTO, контролери, налаштування безпеки та точка входу не виключені.
Звіт: `target/site/jacoco/index.html`.
Невиконання порога завершує `verify` з BUILD FAILURE.

Інтеграційний тест із першої лабораторної збережений і запускається окремо:

```bash
./mvnw -Pintegration-tests verify
```

Він використовує Spring-контекст і H2; його виконання не збільшує unit-покриття JaCoCo.

## Відповідність критеріям

| Критерій | Реалізація |
| --- | --- |
| AC1 | AssertJ перевіряє DTO, поля, HTTP-відповіді, моделі сторінок та повідомлення |
| AC2 | Порожній каталог, відсутня послуга, помилки repository, помилки форм та некоректні claims |
| AC3 | MockitoExtension, @Mock repository/service, @InjectMocks; unit-тести без Spring-контексту |
| AC4 | check-mutation.sh: успішний тест → assertion failure після мутації → відновлення → успішний тест |
| AC5 | Repository замоканий; немає реальної БД, HTTP-запитів, файлових операцій чи Thread.sleep у unit-тестах; час фіксований |
| AC6 | Назви method_scenario_expectedResult; Arrange–Act–Assert у тестах |
| AC7 | verify перевіряє виклики; ArgumentCaptor перевіряє сутності в save/delete |
| AC8 | Звичайні та граничні/відмовні сценарії для кожного публічного методу CatalogService |

## Основна бізнес-логіка

| Метод | Звичайний сценарій | Граничний або відмовний сценарій |
| --- | --- | --- |
| findAll | Мапінг списку й сортування за ID | Порожній список; repository недоступний |
| findById | Повертаються всі поля послуги | 404 і текст причини; помилка repository |
| create | Мапінг, save та присвоєний ID | Необов’язковий опис null; repository відхиляє запис |
| update | Зміна полів із збереженням ID | Відсутня послуга; відмова save |
| delete | Видаляється саме завантажена сутність | Відсутня послуга; відмова delete |

Обмеження полів DTO виконуються MVC-валідацією під час HTTP-запиту;
прямий виклик сервісу у unit-тесті не запускає MVC та Spring Security.
Unit-тести не стверджують, що @PreAuthorize виконується без Spring-проксі:
авторизацію перевіряє збережений інтеграційний тест.
MapStruct — справжній stateless mapper під @Spy, repository — @Mock.
Це дозволяє перевіряти результат мапінгу, не підключаючи базу.

## Доказ навмисної помилки

```bash
bash scripts/check-mutation.sh
```

Скрипт тимчасово прибирає `mapper.update(request, item)` із методу update.
Через це DTO містить старі назву й ціну, а тест очікує нові значення та падає.
Перевіряється саме assertion failure, а не помилка компіляції чи запуску.
Оригінальний файл відновлюється також при аварійному виході зі скрипта.

Після успішного виконання `docs/mutation-evidence` містить:

- `01-baseline.log` — початковий успішний тест.
- `02-mutated.log`, `02-mutated-test.txt` — фактичне падіння assertion.
- `mutation.diff` — точна тимчасова зміна реалізації.
- `03-restored.log` — успішний тест після відновлення.
- `04-full-verification.log` — весь набір та JaCoCo після відновлення.
- `RESULT.txt` — підсумок фактично виконаних перевірок.
- `coverage-summary.txt` — фактичне unit-покриття з CSV-звіту JaCoCo.

Ці текстові журнали та diff є доказом AC4. За потреби можна зробити
скриншот `02-mutated-test.txt` та підсумку успішного повторного запуску.
У гілку комітяться лише коректний код і журнали перевірки; мутація не залишається в реалізації.
